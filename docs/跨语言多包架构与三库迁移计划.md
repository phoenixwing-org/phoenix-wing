# Phoenix Wing 跨语言多包架构与三库迁移计划

> 状态：已决策，分阶段实施。本文是 `phoenix-wing`、`kt-auto-code`、`phoenix-desk-tools` 三库共享边界、包结构、Rust 源码发布和版本兼容的唯一权威总计划。各产品仓库只维护自己的接入/迁出步骤，不复制本文件的公共契约。

## 1. 目标与已确认决策

Phoenix Wing 从“共享 TypeScript/Vue 工具库”升级为“Phoenix 跨语言共享核心与 UI 底座”：

- 一个 `phoenix-wing` Git 仓库承载多个按需安装的 npm 子包和一个 Cargo workspace。
- Code/CAD 纯算法、跨宿主契约、数据库 Schema 与迁移契约、Rust CAD 源码只有一份真源。
- `kt-auto-code` Git 仓库产出两个 VSIX，不增加第四个 Git 仓库；`kt-auto-cad` 依赖 `kt-auto-code`，并向基础插件的同一个 View Container 贡献 CAD Views，不增加 Activity Bar 图标。
- `phoenix-desk-tools` 继续产出 Web/Tauri 聚合产品。
- Rust 源码随专用 npm 子包发布，消费端在构建阶段自行编译；最终用户安装预编译产物。
- npm 安装、应用启动和插件激活阶段均不自动编译 Rust。
- Vue/Pinia/Element Plus 只存在于 UI 子包，不污染 core、contracts 或 Rust source 的消费者。

## 3. npm 子包

首期只拆依赖边界明确的包，避免按文件过度拆分：

| 包 | 职责 | 运行依赖 |
| --- | --- | --- |
| `@phoenix-wing/core` | 任务、日志、设置、Preview/Apply 基础类型与纯工具 | 无 Vue、无宿主 API |
| `@phoenix-wing/code-core` | C++ 排序、UUID、Code Rename、工作集 | `core` |
| `@phoenix-wing/kt-codegen` | 共享 Parameter、17列 CSV/v4 JSON、标记 Analyze 与 CAA/Qt/C++ Renderer | 无宿主 API、无文件 IO、无 UI |
| `@phoenix-wing/cad-contracts` | CAD DTO、JSON Schema、协议和无驱动 Schema v13 只读查询核心 | `core` |
| `@phoenix-wing/cad-core` | CAD 路径、引用图、BOM、诊断、不可变写回计划 | `cad-contracts` |
| `@phoenix-wing/workspace-schema` | `.phoenix` 工作区数据库的版本化 Schema/迁移契约 | 无数据库驱动、无产品路由 |
| `@phoenix-wing/db-node` | 可选 Node 数据库 adapter | Node 专用，不伪装成跨宿主包 |
| `@phoenix-wing/ui-vue` | Vue 组件、composable、CSS token 与壳层 | Vue/Pinia/Element Plus peer deps |
| `@phoenix-wing/cad-rust-source` | Cargo workspace、Rust crates、锁文件、fixture | 构建时 Rust toolchain |

现有仓库根目录的 `phoenix-wing` 包在迁移期继续作为可发布兼容包，维持旧 subpath exports。根 `package.json` 暂不改为 `private`，也不立即搬走 `src/`/Vue SFC；新代码使用细分包。等 Desk Tools 全部切换到 `@phoenix-wing/ui-vue` 后，再决定是否把聚合包搬入 `packages/` 以及废弃周期。

初期所有 Wing 子包统一版本，尤其 `cad-contracts`、`cad-core` 和 `cad-rust-source` 必须锁步发布。独立版本只在依赖图和兼容检测稳定后评估。

## 4. 目标仓库结构

```text
phoenix-wing/
├── package.json                    # 现有 phoenix-wing 兼容发布包，R1 保留
├── src/                            # 现有入口/SFC，迁移期显式 re-export
├── packages/
│   ├── core/
│   ├── code-core/
│   ├── kt-codegen/
│   ├── cad-contracts/
│   ├── cad-core/
│   ├── workspace-schema/
│   ├── db-node/
│   ├── ui-vue/
│   ├── cad-rust-source/
│   │   ├── package.json
│   │   ├── Cargo.toml
│   │   ├── Cargo.lock
│   │   └── crates/
│   │       ├── fcstd-reader/
│   │       ├── fcstd-xlink/
│   │       ├── fcstd-query/
│   │       └── fcstd-cli/
├── pnpm-workspace.yaml
└── docs/
```

迁移不要求一次性移动当前 `src/`。先建立 workspace 与包边界，再按包逐个迁移，并为旧入口保留显式 re-export。新 TypeScript 子包必须发布 `dist/*.js` 和 `.d.ts`；当前聚合包直接导出源码只作为兼容过渡，不复制到新包。

`@phoenix-wing/core` 采用白名单提取，不能把现有 `src/utils` 整目录搬入：DOM 色彩/拖拽/浏览器存储、Vue `Ref` 属性 Schema 和依赖 Vue 的 Workbench 均归 UI/浏览器层。只有经依赖检查确认不使用 DOM、Vue、Node 和宿主 API 的模块才能进入 core。

## 5. Rust 源码边界

### 5.1 迁入

| 当前 Desk Tools 来源 | Wing 目标 | 处理 |
| --- | --- | --- |
| `server/fcstd-reader` | `cad-rust-source/crates/fcstd-reader` | 纯 FCStd ZIP/XML 读取与写回 |
| `server/fcstd-xlink` | `cad-rust-source/crates/fcstd-xlink` | XLink/Label 扫描与受控 patch |
| `server/cli` | `cad-rust-source/crates/fcstd-cli` | 稳定 JSON CLI；不包含产品路径发现 |
| `server/fcstd-query` | `cad-rust-source/crates/fcstd-query` | 已随数据库 Schema 迁入并切换真源 |

`fcstd-query` 原先硬编码 `phoenix_cad_*` 表，不是独立的 FCStd 算法。下列内容现已一并进入 Wing：

1. Schema DDL 与版本常量；
2. 数据库兼容/迁移规则；
3. 查询输入输出 JSON Schema；
4. Desk Tools 与 `kt-auto-cad` 的共同 fixture。

### 5.2 不迁入

- Hono 路由、Tauri command、VS Code API、Node `fs` 路径发现。
- FreeCADCmd、SolidWorks COM 和应用生命周期管理。
- 产品设置、窗口状态、HTTP endpoint 与界面状态。

### 5.3 编译和发布

`@phoenix-wing/cad-rust-source` 的 npm `files` 至少包含 `Cargo.toml`、统一的 workspace `Cargo.lock`、`crates/`、契约 Schema、LICENSE 和 NOTICE。当前 `fcstd-reader` 没有自己的 `Cargo.lock`，迁入时必须由 workspace 统一生成并提交。禁止 `postinstall` 编译。

该包必须公开稳定的 manifest 定位入口，例如导出 `./source-manifest.json` 和 `./Cargo.toml`；消费脚本通过 Node package resolution 获取位置，不能猜测 pnpm store 或 `node_modules` 实体路径。

消费端显式运行：

```bash
CARGO_TARGET_DIR=<consumer-cache> \
  cargo build --release --locked \
  --manifest-path <cad-rust-source>/Cargo.toml
```

消费端负责把对应平台二进制复制进 VSIX/Tauri resources；不得在运行时依赖相邻 Git 仓库。

## 6. 契约与数据库

### 6.1 契约形式

CAD 跨语言边界使用可序列化、带版本的 JSON：

- JSON Schema 是字段、必填项和兼容性的真源；
- TypeScript 类型与 Rust `serde` 类型必须通过同一组 fixture；
- CLI stdout 只输出协议 JSON，诊断写 stderr；
- 每个 CLI 提供 `--protocol-version` 和机器可读能力清单；
- 发现信息同时声明首选 `protocol_version` 与 `supported_protocol_majors`，宿主按主版本集合交集协商；
- v1 JSON 中的数值必须是有限值，NaN/Infinity 在 envelope 边界返回稳定错误，不序列化成 `null`；
- 新增可选字段保持向前兼容，删除/改义字段提升协议主版本。

### 6.2 Preview/Apply

所有写盘核心遵守两阶段契约：

```text
analyze(input, snapshot) -> immutable plan + diagnostics
apply(plan, currentSnapshot) -> applied/skipped/conflict report
```

Host 必须在 apply 前检查文件指纹，并由用户明确确认。Wing core 不弹窗、不选择工作区、不读取产品设置。

### 6.3 数据库职责

- Wing：`workspace-schema` 持有表/索引 DDL、Schema 版本和迁移规则；`cad-contracts` 持有领域查询协议、无驱动参数化只读查询核心和 fixture；`db-node` 只提供可选 Node adapter。
- Desk Tools：Node/Tauri 数据库连接、Web API、长任务和产品缓存。
- KT Auto CAD：VS Code 工作区数据库 adapter、工作区信任和远程环境门禁。
- 任一宿主遇到未知主版本都必须阻止写入，不能猜测迁移。

## 7. UI 分层

Wing 不整体改写为原生 HTML，也不要求所有产品使用 Vue：

- `core`/contracts 提供可序列化 ViewModel 和任务状态；
- CSS token、主题变量和图标可被任意 Webview/Web 应用消费；
- `ui-vue` 保留 Desk Tools 所需的 Vue 组件；
- VS Code 可继续使用原生 HTML/CSS/JS；只有已有两个真实消费者且交互一致的组件才提升为共享 UI。

Element Plus 只能作为 `ui-vue` 的 peer dependency，不能出现在 `core`、`cad-*`、`code-core` 或 Rust source 的依赖图中。

## 8. 依赖方向

允许：

```text
products -> host adapters -> domain core -> contracts -> core
products -> ui-vue
product build -> cad-rust-source
cad-core -> cad-contracts -> core
db-node -> workspace-schema
```

禁止：

```text
core/contracts/domain core -> vscode/tauri/hono/vue/node fs
code-core <-> cad-core
Wing -> 任一产品仓库
产品运行时 -> 相邻 Git 仓库
应用激活/postinstall -> cargo build
```

## 10. 提交与变更纪律

三库使用可独立验证的中文提交，推荐顺序：

1. `docs(wing): 明确跨语言多包架构与三库职责`
2. `docs(auto-cad): 制定同仓双插件实施计划`
3. `docs(desk-tools): 固化 CAD 核心迁出与消费步骤`
4. `build(wing): 建立 pnpm 与 Cargo 工作区骨架`
5. `feat(wing): 建立 CAD 契约包`
6. `refactor(wing): 迁入 FCStd 与 XLink Rust 核心`

每次迁移采用“复制并锁定 fixture → 消费端切换 → 删除旧真源”三步，不在同一提交中同时改变算法语义、宿主 UI 和发布方式。

## 11. 总体验收

1. 三个 Git 仓库之外不新增共享源码仓库。
2. 用户能按需安装 npm 子包，不因使用 core 被迫安装 Vue/Element Plus 或 Rust 二进制。
3. Wing npm 发布物中的 Rust source 可在干净环境用锁文件编译。
4. `kt-auto-code`、`kt-auto-cad`、Desk Tools 只保留各自 Host adapter 和产品 UI。
5. 同一 FCStd/XLink/数据库 fixture 在两个宿主产生一致协议结果。
6. 所有写盘都有预览、确认、指纹冲突检测、取消和审计报告。
7. 发布 VSIX/Tauri 的最终用户无需 Node、Cargo、Python 或相邻源码仓库（外部 FreeCAD/SolidWorks 功能除外）。
