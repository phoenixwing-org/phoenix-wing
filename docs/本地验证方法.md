# 本地验证与消费者并列联调

状态：current

Owner：Phoenix Wing maintainers

适用版本：Wing 0.6.x–0.7.x / Auto Code 0.5.x / Desk Tools 0.2.x

最后核验：2026-08-28

## Node 与 pnpm 基线

Phoenix Wing 的开发、CI 与本地消费者源码联调统一使用 Node 22 和 pnpm 10.15.1。进入仓库后先执行：

```bash
nvm use
node --version
pnpm --version
```

根 `.nvmrc` 固定 Node 22 主版本，`package.json#packageManager` 固定 pnpm 10.15.1，GitHub Actions 同样使用 Node 22。若 `nvm use` 提示本机尚未安装，先执行 `nvm install 22`；不得因当前 shell 仍停留在 Node 20 就把本地联调结果写成统一环境验收。

## 目标与唯一标准目录

Wing 自身的包测试、tarball smoke 与消费者本地源码联调是两类门禁。前者只需要 `phoenix-wing` checkout；后者要求每个消费者都能通过同级 `../phoenix-wing` 找到唯一明确的本地真源。例如：

```text
phoenix/
├── phoenix-wing/                 # 主库 develop，默认本地消费真源
├── kt-auto-code/
├── phoenix-admin-vue/
├── phoenix-dev-hub/
├── phoenix-desk-tools/
├── phoenix-function-develop/
└── phoenix-open-issue/
```

若消费者位于其他根目录，可在消费者旁建立名为 `phoenix-wing` 的文件系统目录链接，默认指向已提升的主库。Windows 同盘目录推荐使用不需要管理员权限的 Junction。文件系统链接只解决稳定路径，不得替代 Git 工作流：未完成修改仍在独立 working worktree 开发，验证、提交归档并提升到主库 `develop` 后，消费者链接继续读取主库。不要把消费者长期绑在移动中的功能 worktree。

所有消费者的根级开发命令统一如下：

| 命令 | Wing 真源 | 约束 |
|---|---|---|
| `pnpm dev` | Registry | 严格使用 manifest 与 lockfile 的精确版本，并清除本地模式环境变量 |
| `pnpm wing` | 同级 `../phoenix-wing` | 校验并构建本地源码，失败时停止，绝不静默回退 Registry |

旧的根级 `pnpm dev:registry`、`pnpm dev:local-wing`、`pnpm dev:wing-local` 入口删除，不再作为别名保留。专项测试、构建与发布门禁可以继续使用 `*:registry` / `*:local-wing` 后缀，但不能改变上述两个启动入口的含义。

本规范不把自定义绝对路径作为 AI 的默认分支。AI 找不到同级仓库时应报告上面的目录要求和实际缺失路径，然后停止本地联调；若目标只是验证已发布 npm 包，应明确改用下表的 Registry 对照命令，而不能用 Registry 结果证明本地 Wing 改动。

## Auto Code：双插件本地 Wing 联调

在 `kt-auto-code` 根目录执行：

| 目的 | 命令 | Wing 真源与行为 |
|---|---|---|
| Registry 开发启动 | `pnpm dev` | 清除本地模式，使用 `package.json` 与 lockfile 的 Registry 精确版本并启动插件 |
| 本地 Wing 开发启动 | `pnpm wing` | 严格使用 `../phoenix-wing`，构建 Wing 后构建并启动 Auto Code；不要求可选 CAD 仓库 |
| AI/CI 无 GUI 验证 | `pnpm ext:dev:prepare` | 使用同一并列 Wing，构建两个插件并验证 bundle 来源，不启动 VS Code |
| Registry 无 GUI 对照 | `pnpm ext:dev:registry:prepare` | 使用 Registry 精确版本完成构建和来源对照，不启动 VS Code |

AI 验证 Wing 改动时优先运行 `pnpm ext:dev:prepare`；需要用户在 Extension Development Host 中交互时才运行 `pnpm wing`。本地入口缺少同级 Wing 时应停止并提示目录要求；`pnpm dev` 始终是正式 Registry 开发入口。

Auto 的构建包装器会检查 Wing 身份与必需包、重建本地 `dist`、验证 Code/CAD bundle 的 esbuild metafile，并确认消费者 `node_modules` 命中为 0。实现细节和既有验收见 Auto Code 的[《本地 Wing 并列开发》](https://gitee.com/phoenixwing/kt-auto-code/blob/master/docs/%E6%9C%AC%E5%9C%B0Wing%E5%B9%B6%E5%88%97%E5%BC%80%E5%8F%91.md)；并列 checkout 中对应文件为 `../kt-auto-code/docs/本地Wing并列开发.md`。

## Desk Tools：Server、Web、测试与 bundle

在 `phoenix-desk-tools` 根目录按目标执行：

| 目的 | 本地 Wing 命令 | Registry 对照命令 |
|---|---|---|
| 启动 Server + Web | `pnpm wing` | `pnpm dev` |
| 消费端测试 | `pnpm test:local-wing` | `pnpm test:registry` |
| Web + Server bundle | `pnpm build:local-wing` | `pnpm build:registry` |

三个本地命令都必须校验并构建同级 `../phoenix-wing`。`pnpm wing` 同时启动 Node Server 与 Vite Web；测试和构建命令使用同一受控 exports resolver。若同级目录不存在或结构不完整，命令必须停止并提示直接使用 `pnpm dev` 或对应 Registry 测试/构建命令，不能自动改测发布包。

## 其他 Phoenix 消费者

- Phoenix Admin Vue、Phoenix Dev Hub 与 Phoenix Function Develop：`pnpm dev` 启动 Registry，`pnpm wing` 启动并列源码。
- Open Issue：两个命令都会先安全挂载插件并启动 Admin Node/Vue Host；区别只在 Vue Host 的 Wing 真源。
- 不直接加载 Phoenix Wing 的纯后端或资源仓库不增加空的 `pnpm wing` 占位命令。

Desk 的包装器只在当前子进程注入本地 alias/resolver，Web、Server Vitest 与 bundle 使用同一包 exports 规则；Registry 模式则清除本地模式并严格使用清单与锁文件。实现细节和既有验收见 Desk Tools 的[《Wing 并列仓库联调》](https://gitee.com/phoenixwing/phoenix-desk-tools/blob/develop/docs/platform/Wing%E5%B9%B6%E5%88%97%E4%BB%93%E5%BA%93%E8%81%94%E8%B0%83.md)；并列 checkout 中对应文件为 `../phoenix-desk-tools/docs/platform/Wing并列仓库联调.md`。

## 不修改依赖图的安全边界

本地联调是构建期来源切换，不是安装方式。任何人工或 AI 流程都必须满足：

- 不运行 `pnpm link` 或 `pnpm link --global`；
- 不执行 `pnpm add file:...`，不写入 `link:`、`file:` 或本地 `workspace:` 依赖；
- 不在 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml` 或 `pnpm.overrides` 中加入本地 Wing 路径；
- 不复制、替换、编辑消费者 `node_modules` 中的 Wing 发布包；
- 不用未受控的 shell 环境变量配合普通 build/test 命令绕开来源门禁；
- 本地命令完成后再次确认消费者 manifest、lockfile 与 `node_modules` 没有被改写。

旧文档曾建议临时把 `../phoenix-wing` 写入消费者 `pnpm-workspace.yaml`；该方案已废止，不能继续使用。当前 Auto 与 Desk 包装器会在单次进程内解析本地 Wing，提交态依赖始终保持 Registry 精确版本。

## Wing 自身门禁与发布边界

只验证 Wing checkout 时使用仓库自身命令，不需要消费者目录：

```bash
pnpm verify:ci
pnpm verify:package-tarballs
```

`verify:ci` 覆盖文档、架构、构建、workspace 测试、类型检查、发布矩阵与 tarball；`verify:package-tarballs` 在全新临时 npm 消费目录验证聚合 UI 与小包公共入口。需要证明真实消费者能加载尚未发布的 Wing 改动时，才进入上面的 Auto/Desk 并列流程。

聚合构建只为实际会 emit JavaScript 的 `.ts` 建立 Vite entry；纯类型模块仍由 `vue-tsc`
输出 `.d.ts`，不得用 Rollup 空 chunk 充当运行时入口。`phoenix-wing/types/*` wildcard 只承载
`import type`，包含运行时 schema 检查的 `phoenix-wing/types/PnwRibbonConfig` 使用精确 export。
`verify:aggregate-dist` 和 `verify:package-tarballs` 会同时检查：纯类型 `.js` 不存在、`.d.ts`
完整、类型子路径可被干净 TypeScript consumer 解析、运行时精确子路径仍可加载。

本地消费者通过不代表 npm Registry 已发布，也不授权修改版本、移动标签或发布包。正式发布验收仍必须依次证明 tarball、Registry 查询、消费者精确版本升级和真实宿主行为。

## 已有消费者验收与本步骤范围

2026-07-18，Auto Code 专题已经记录 `pnpm ext:dev:prepare`、双插件来源门禁和 `pnpm ext:dev:registry:prepare` 对照通过；Desk Tools 专题已经记录本地 Server/Web 启动、`pnpm build:local-wing`、本地 resolver 测试与 Registry 对照通过。以上结果的测试数量和日志以两个消费者专题为准，本次 Wing 文档治理不重复执行、也不重新声称消费者代码测试。

后续修改 Wing 后，应按改动的真实消费者选择最小充分命令：

1. Auto Code/Auto CAD 能力：先运行 `pnpm ext:dev:prepare`，需要交互再运行 `pnpm wing`；
2. Desk Web/Server 能力：运行 `pnpm test:local-wing` 与 `pnpm build:local-wing`，需要交互再运行 `pnpm wing`；
3. 发布物对照：运行相应 `*:registry` 命令，结果与本地来源分开记录；
4. 目录缺失：说明标准并列布局并停止；允许建立明确指向主库的文件系统目录链接，但不创建 `pnpm link`、依赖 override 或 node_modules 补丁。
